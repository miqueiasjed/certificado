# Task 9.1 - Migration: periodicidade com unidade e vínculo da OS com o contrato

## Objetivo

Dar unidade à periodicidade do contrato (dias, semanas, meses) e criar o vínculo que identifica a OS gerada a partir de um contrato.

## Tipo

backend-estrutura

## Arquivos a criar/modificar

- `database/migrations/*_add_periodicity_unit_to_contracts.php` -> criar
- `database/migrations/*_add_contract_link_to_work_orders.php` -> criar
- `app/Models/Contract.php` -> modificar

## Contexto necessário (ler antes)

- `database/migrations/2025_11_03_120800_update_contracts_table_for_new_requirements.php` -> **`visit_frequency` foi convertida de `integer` para `string(50)` em produção**
- `app/Models/Contract.php` -> fillable e casts atuais
- `app/Models/WorkOrder.php` -> fillable, casts e enum de `status`
- `CLAUDE.md` -> regra de migration em tabela com dado existente

## Skills necessárias

- `laravel-arquitetura`
- `datas-timezone`

## Especificação

### O que fazer

1. **Antes de escrever a migration**, levantar os valores reais de `visit_frequency` em produção: `select distinct visit_frequency, count(*) from contracts group by visit_frequency`. A coluna é string livre hoje e pode conter `"3"`, `"3 meses"`, `"trimestral"` ou vazio. O resultado desse levantamento decide o mapeamento e **precisa aparecer no relatório da task**.

2. Migration em `contracts`:
   - `visit_frequency_valor` (unsignedInteger, nullable) -> número puro
   - `visit_frequency_unidade` (string 10, nullable) -> `dias`, `semanas`, `meses`
   - **Sem** backfill nesta migration e **sem** remover `visit_frequency`. A coluna antiga fica intocada: ela é a fonte do backfill da Task 9.2 e a rede de segurança se algo der errado.

3. Migration em `work_orders`:
   - `contract_id` (nullable, FK `contracts`, `nullOnDelete`)
   - `origem` (string 20, nullable) -> `contrato` para OS gerada, nulo para OS criada à mão
   - `visita_numero` (unsignedInteger nullable) -> a enésima visita do contrato
   - Índice composto `[contract_id, scheduled_date]`, usado pela verificação de idempotência
   - Unique composto `[contract_id, visita_numero]` **não** entra: reprogramação pode renumerar, e o unique travaria. A idempotência é garantida no Service (Task 9.3)

4. `Contract`: acrescentar os campos novos ao fillable, criar a relação `workOrders(): HasMany` e o accessor `periodicidadeEmDias()` que converte valor e unidade.

### Regras de negócio aplicáveis

- Não remover nem alterar `visit_frequency` neste deploy. A conversão de integer para string já aconteceu uma vez nessa coluna em produção; mexer de novo antes do backfill conferido é risco desnecessário.
- Colunas nullable, sem default: contrato existente continua com os campos novos vazios até o backfill, e nada no sistema lê os campos novos ainda.
- `origem` distingue OS gerada de OS criada à mão. Sem isso, cancelar visitas futuras de um contrato varreria OS que alguém criou manualmente.

### Critérios de aceitação

- [ ] O levantamento dos valores de `visit_frequency` em produção está no relatório
- [ ] As colunas novas existem em `contracts` e `work_orders`
- [ ] `visit_frequency` continua intocada
- [ ] `migrate:rollback` remove só as colunas novas
- [ ] `php artisan test` continua passando
- [ ] A aplicação funciona exatamente como antes: criar contrato e OS sem diferença
