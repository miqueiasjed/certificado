# Task 4.6 - Trait BelongsToCompany e resolvedor de tenant

## Objetivo

Criar o escopo global por empresa, com preenchimento automático de `company_id` na criação, e o resolvedor único do tenant corrente.

## Tipo

backend-logica

## Arquivos a criar/modificar

- `app/Support/TenantAtual.php` -> criar
- `app/Models/Concerns/BelongsToCompany.php` -> criar

## Contexto necessário (ler antes)

- `app/Support/DominioMultiempresa.php` -> lista de models de domínio
- `.claude/prd/saas-multitenant.md` -> regras 2, 4 e 5 do modelo de isolamento

## Especificação

### O que fazer

1. `App\Support\TenantAtual` (final, estado estático):
   - `id(): ?int` -> devolve o tenant definido explicitamente; se não houver, `auth()->user()?->company_id`; se não houver usuário, `null`
   - `definir(int $companyId): void` -> fixa o tenant explicitamente (usado por comando artisan, seeder, fila e pelo "assumir tenant" do Plano 5)
   - `limpar(): void`
   - `comTenant(int $companyId, Closure $callback): mixed` -> define, executa, restaura o valor anterior mesmo em caso de exceção (`try/finally`)
   - `semEscopo(Closure $callback): mixed` -> executa com o escopo global desligado, para uso do super admin e de rotina de plataforma. Sinalizador próprio, lido pela trait
   - `exigirId(): int` -> devolve o id ou lança exceção com mensagem explícita. Usado onde operar sem tenant é bug

2. `App\Models\Concerns\BelongsToCompany`:
   - `bootBelongsToCompany()`:
     - `addGlobalScope('company', ...)` aplicando `where {$tabela}.company_id = TenantAtual::id()` quando houver tenant e o modo `semEscopo` estiver desligado. Sempre prefixar a coluna com a tabela: sem o prefixo, qualquer `join` com outra tabela que tenha `company_id` gera "column ambiguous"
     - `creating` -> preenche `company_id` com `TenantAtual::id()` se o atributo estiver vazio
   - Relação `company(): BelongsTo`
   - `scopeDeTodasAsEmpresas($query)` -> `withoutGlobalScope('company')`, para uso explícito e raro

3. Exceção declarada do model `User`: o escopo global **não** se aplica na autenticação, senão o login não encontra o usuário antes de existir tenant. Implementar a trait em `User` apenas para o preenchimento na criação, sem o escopo global de leitura, e comentar o motivo no código.

### Regras de negócio aplicáveis

- Sem tenant resolvido, o escopo **não** filtra nada. Isso é deliberado para migration, seeder e teste, e é exatamente por isso que a Task 4.11 (teste de vazamento) é obrigatória: ela é a rede que pega o caso em que o tenant não foi resolvido em uma requisição real.
- `semEscopo()` é a única porta de saída do isolamento. Toda chamada dela em código de domínio precisa de comentário justificando.
- A trait não é aplicada a nenhum model nesta task. Isso é a Task 4.8.
- Nenhum comportamento observável muda enquanto existir um único tenant.

### Critérios de aceitação

- [ ] `TenantAtual::comTenant(2, fn () => ...)` restaura o valor anterior mesmo se o callback lançar exceção
- [ ] Model com a trait recebe `company_id` automaticamente ao ser criado dentro de um tenant
- [ ] Query em model com a trait filtra por `company_id` quando há tenant
- [ ] `deTodasAsEmpresas()` traz registros de todos os tenants
- [ ] `join` entre dois models com a trait não gera erro de coluna ambígua
- [ ] `php artisan test` continua passando
