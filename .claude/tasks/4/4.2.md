# Task 4.2 - Etapa 1: company_id nullable em todas as tabelas de domínio

## Objetivo

Adicionar a coluna `company_id` nullable, sem chave estrangeira e sem índice, em todas as tabelas de domínio. Primeiro deploy da migração multiempresa.

## Tipo

backend-estrutura

## Arquivos a criar/modificar

- `database/migrations/*_add_company_id_to_domain_tables.php` -> criar

## Contexto necessário (ler antes)

- `app/Support/DominioMultiempresa.php` -> lista de tabelas, criada na Task 4.1
- `.claude/prd/saas-multitenant.md` -> "Ordem da migração (não destrutiva)", passo 1
- `CLAUDE.md` -> regra de migration em tabela com dado existente

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

1. Migration única percorrendo `DominioMultiempresa::TABELAS_DE_DOMINIO`:
   ```php
   foreach (DominioMultiempresa::TABELAS_DE_DOMINIO as $tabela) {
       if (! Schema::hasTable($tabela) || Schema::hasColumn($tabela, 'company_id')) {
           continue;
       }
       Schema::table($tabela, function (Blueprint $t) {
           $t->unsignedBigInteger('company_id')->nullable()->after('id');
       });
   }
   ```
2. `down()` remove a coluna das mesmas tabelas, com a mesma guarda de existência.
3. Sem `foreign()`, sem `index()`, sem `default`. Os três entram na Task 4.4.
4. Imprimir, ao final do `up()`, a contagem de tabelas alteradas e a de tabelas puladas.

### Regras de negócio aplicáveis

- Coluna nullable sem FK e sem índice é a alteração mais barata possível em MySQL: nenhuma linha é reescrita para validação de restrição. É por isso que ela é um deploy sozinha.
- Nenhum código lê ou escreve `company_id` ainda. O sistema continua se comportando exatamente como antes deste deploy, e é isso que precisa ser confirmado em produção antes de seguir para a Task 4.3.
- Migration idempotente: rodar de novo não quebra e não duplica coluna.
- Não incluir `companies` nem tabela pivot.

### Critérios de aceitação

- [ ] `php artisan migrate` adiciona `company_id` a todas as tabelas da lista
- [ ] `php artisan migrate:rollback` remove a coluna de todas, sem erro
- [ ] Rodar `migrate` duas vezes seguidas não gera erro
- [ ] Nenhuma tabela pivot recebeu a coluna
- [ ] `php artisan test` continua passando
- [ ] A aplicação funciona exatamente como antes: criar OS, emitir certificado e lançar financeiro sem diferença

## Teste esperado

- Comando: `php artisan migrate && php artisan test`
- Verificação manual em produção: após o deploy, criar uma OS de teste e conferir que `company_id` fica nulo sem quebrar nada

## Estimativa

baixa - ~60 linhas | 1 arquivo

## Plano de retorno

`php artisan migrate:rollback --step=1`. Como nenhuma coluna é lida por código, o retorno é imediato e sem perda de dado.
