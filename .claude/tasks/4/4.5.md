# Task 4.5 - Etapa 4: uniques globais viram compostos com company_id

## Objetivo

Converter as uniques globais que quebrariam com o segundo tenant em uniques compostas com `company_id`.

## Tipo

backend-estrutura

## Arquivos a criar/modificar

- `database/migrations/*_compose_uniques_with_company_id.php` -> criar

## Contexto necessário (ler antes)

- `app/Support/DominioMultiempresa.php` -> `UNIQUES_A_COMPOR`
- `.claude/prd/divida-tecnica.md` -> item 3, com o efeito de cada unique
- `database/migrations/` -> conferir o nome real de cada índice atual antes de dropar

## Skills necessárias

- `laravel-arquitetura`

## Especificação

### O que fazer

Para cada entrada de `UNIQUES_A_COMPOR`:

1. `dropUnique` do índice atual pelo nome real (conferir com `SHOW INDEX FROM <tabela>`; o nome gerado pelo Laravel segue `tabela_coluna_unique`, mas migrations antigas podem ter nome próprio).
2. Criar `unique(['company_id', <coluna>])`.

As cinco obrigatórias:

| Tabela | Unique atual | Vira |
|---|---|---|
| `daily_cash_balances` | `balance_date` | `[company_id, balance_date]` |
| `work_orders` | `order_number` | `[company_id, order_number]` |
| `service_orders` | `order_number` | `[company_id, order_number]` |
| `technicians` | `email` | `[company_id, email]` |
| `service_types` | `slug` | `[company_id, slug]` |

3. `users.email` **não** é tocada: continua unique global por decisão registrada no PRD.
4. `down()` desfaz, recriando a unique simples. Atenção: o `down()` só funciona se não houver duplicata entre tenants no momento do retorno. Documentar isso no comentário da migration.
5. Antes de criar cada unique composta, conferir que não existe duplicata de `[company_id, coluna]`. Se existir, abortar com a lista dos valores duplicados, sem alterar nada.

### Regras de negócio aplicáveis

- Esta é a etapa que o plano marca como "quebra silenciosamente se for esquecida". `daily_cash_balances.balance_date` é a mais perigosa: com dois tenants, o segundo não cria o saldo do dia e o financeiro dele falha sem erro visível.
- A geração de `order_number` no código também precisa passar a considerar o tenant. Conferir `WorkOrderService` e `ServiceOrderService`: se a numeração vem de `max(order_number) + 1` global, ela precisa de `where company_id`. Se a alteração for necessária, **reportar**, porque ela pertence à Task 4.8 (models com escopo) e não a esta migration.
- Com um único tenant, a unique composta se comporta igual à simples. Nenhum efeito observável em produção neste deploy.

### Critérios de aceitação

- [ ] As cinco uniques viraram compostas
- [ ] `users.email` continua unique simples
- [ ] Migration aborta com lista de duplicatas se houver conflito
- [ ] Inserir dois `daily_cash_balances` com a mesma data em empresas diferentes funciona
- [ ] Inserir dois com a mesma data na mesma empresa continua falhando
- [ ] Relatório da task diz se a geração de `order_number` precisa de ajuste
