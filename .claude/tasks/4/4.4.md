# Task 4.4 - Etapa 3: company_id NOT NULL, índice e chave estrangeira

## Objetivo

Tornar `company_id` obrigatório, indexado e com integridade referencial, depois que o backfill foi conferido.

## Tipo

backend-estrutura

## Arquivos a criar/modificar

- `database/migrations/*_make_company_id_required_on_domain_tables.php` -> criar

## Contexto necessário (ler antes)

- `app/Support/DominioMultiempresa.php` -> lista de tabelas
- `.claude/tasks/4/4.3.md` -> o backfill precisa estar conferido antes desta migration
- `.claude/prd/saas-multitenant.md` -> passo 3 da ordem de migração

## Skills necessárias

- `laravel-arquitetura`

## Especificação

### O que fazer

1. No início do `up()`, **abortar** se qualquer tabela de domínio ainda tiver `company_id` nulo:
   ```php
   foreach (DominioMultiempresa::TABELAS_DE_DOMINIO as $tabela) {
       $nulos = DB::table($tabela)->whereNull('company_id')->count();
       if ($nulos > 0) {
           throw new RuntimeException("A tabela {$tabela} tem {$nulos} registros sem company_id. Rode multiempresa:backfill antes.");
       }
   }
   ```
   Essa guarda é o que impede a migration de falhar no meio, deixando metade das tabelas com restrição e metade sem.

2. Para cada tabela: `change()` da coluna para `unsignedBigInteger('company_id')->nullable(false)`, criar índice `index('company_id')` e a FK para `companies.id` com `restrictOnDelete()`.

3. FK com `restrictOnDelete`, nunca `cascadeOnDelete`: apagar um tenant por engano não pode levar junto todo o dado dele. Exclusão de tenant é fluxo de negócio do Plano 5, com regra própria.

4. `down()` remove FK e índice e volta a coluna para nullable.

5. Migration idempotente: pular tabela que já tenha a FK.

### Regras de negócio aplicáveis

- Só roda depois de a Task 4.3 ter sido executada em produção e o relatório conferido. Ordem invertida derruba a migration em produção.
- Em MySQL, `change()` em coluna de tabela grande reescreve a tabela. Rodar em janela de baixo movimento e medir o tempo em um dump de produção antes.
- `users` também recebe a FK: um usuário sem empresa não pode existir depois desta etapa.
- Nada de `default(1)` na coluna. Padrão silencioso mascara bug de tenant não resolvido, que é exatamente a falha mais grave possível aqui.

### Critérios de aceitação

- [ ] Migration aborta com mensagem clara se houver `company_id` nulo em qualquer tabela
- [ ] Após rodar, todas as tabelas de domínio têm `company_id` NOT NULL, indexado e com FK
- [ ] Tentar inserir registro com `company_id` inexistente falha por FK
- [ ] Tentar excluir a empresa 1 falha por `restrictOnDelete`
- [ ] `php artisan migrate:rollback` volta tudo a nullable sem perda de dado
- [ ] `php artisan test` continua passando

## Teste esperado

- Comando: `php artisan migrate && php artisan test`
- Verificação manual: em cópia do banco de produção, medir o tempo total da migration antes de aplicar no ambiente real

## Estimativa

média - ~90 linhas | 1 arquivo

## Plano de retorno

`php artisan migrate:rollback --step=1` remove FK, índice e obrigatoriedade. O dado preenchido permanece, então o retorno não perde nada e a etapa pode ser refeita.
