# Task 4.11 - Teste de vazamento entre tenants

## Objetivo

Criar o tenant 2 com dados e confirmar que o usuário do tenant 1 não enxerga nada dele em nenhuma tela ou endpoint.

## Tipo

teste

## Arquivos a criar/modificar

- `tests/Feature/VazamentoEntreEmpresasTest.php` -> criar

## Contexto necessário (ler antes)

- `routes/web.php` -> lista completa de rotas de domínio a percorrer
- `app/Support/TenantAtual.php` -> como definir o tenant no teste
- `.claude/prd/saas-multitenant.md` -> passo 6 da ordem de migração

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

Cenário comum a todos os casos: criar as empresas 1 e 2, um usuário administrador em cada, e em cada tenant um conjunto completo de dado (cliente, endereço, cômodo, dispositivo, OS, certificado, contrato, orçamento, lançamento financeiro, produto, técnico).

Casos:

1. **Listagens:** autenticado como usuário do tenant 1, percorrer as rotas `index` de todos os módulos de domínio e afirmar que a resposta **não** contém nenhum id nem identificador dos registros do tenant 2. Varrer as rotas a partir da coleção de rotas registradas, não de uma lista escrita à mão que envelhece.
2. **Acesso direto por id:** `GET`, `PUT` e `DELETE` em cada recurso do tenant 2, autenticado como tenant 1, devolvem 404 (não 403: o recurso não deve nem existir para ele).
3. **Busca:** endpoints de busca (`clients` por nome, `work-orders.by-client`, `devices.by-address`, `rooms.by-address`) não devolvem registro do outro tenant.
4. **Contadores e dashboard:** os totais do dashboard e do dashboard financeiro do tenant 1 não incluem valor do tenant 2.
5. **Numeração:** criar OS nos dois tenants com o mesmo `order_number` funciona; repetir dentro do mesmo tenant falha.
6. **Saldo diário:** criar `daily_cash_balances` da mesma data nos dois tenants funciona. Este é o caso apontado no `divida-tecnica.md` como falha silenciosa.
7. **PDF:** gerar o PDF de um certificado do tenant 2 autenticado como tenant 1 devolve 404.

### Regras de negócio aplicáveis

- Vazamento entre empresas é a falha mais grave possível neste projeto. Este teste é o portão do passo 6 do PRD: só depois de ele passar é que um segundo tenant real entra.
- Caso que não puder ser coberto precisa aparecer no relatório da task como lacuna declarada, nunca ser omitido.
- O caso 1 usa a coleção de rotas para não envelhecer: rota nova de domínio entra na varredura sozinha.

### Critérios de aceitação

- [ ] Os 7 casos passam
- [ ] O caso 1 percorre pelo menos todas as rotas `index` de domínio existentes hoje
- [ ] Remover a trait de um model faz o caso 2 falhar para aquele recurso
- [ ] O teste não depende de dado pré-existente
- [ ] Rotas não cobertas estão listadas no relatório da task

## Teste esperado

- Comando: `php artisan test --filter=VazamentoEntreEmpresasTest`
- Verificação manual: com um segundo tenant em ambiente local, navegar como usuário do tenant 1 e tentar acessar ids do tenant 2 pela URL
