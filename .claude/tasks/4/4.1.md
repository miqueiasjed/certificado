# Task 4.1 - Inventário das tabelas e models de domínio

## Objetivo

Criar a fonte única que declara quais tabelas e models são de domínio (recebem `company_id`) e quais não são, para migrations, trait e testes lerem da mesma lista.

## Tipo

backend-estrutura

## Arquivos a criar/modificar

- `app/Support/DominioMultiempresa.php` -> criar

## Contexto necessário (ler antes)

- `app/Models/` -> listar todos os models e classificar cada um
- `.claude/prd/saas-multitenant.md` -> regra 1: tabela raiz recebe `company_id`, pivot herda pelo pai
- `.claude/prd/divida-tecnica.md` -> item 3, uniques globais que quebram com o segundo tenant

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

Criar `final class DominioMultiempresa` com constantes e métodos estáticos:

1. `TABELAS_DE_DOMINIO: array<string>` -> toda tabela raiz que recebe `company_id`. Levantar percorrendo `app/Models/` e o schema real do banco, não de memória. Inclui, no mínimo: `clients`, `addresses`, `rooms`, `devices`, `device_events`, `pest_sightings`, `work_orders`, `service_orders`, `certificates`, `contracts`, `budgets`, `financial_entries`, `payment_details`, `daily_cash_balances`, `products`, `services`, `service_types`, `technicians`, `event_types`, `bait_types`, `active_ingredients`, `chemical_groups`, `antidotes`, `organ_registrations`, `procedures`, `work_order_adequations`, `work_order_photos`, `audit_logs`, `access_logs`, `users`.

2. `TABELAS_FORA_DO_ESCOPO: array<string>` -> tabela que **não** recebe a coluna, cada uma com o motivo em comentário: `companies` (é a própria tabela de tenants), tabelas pivot (`work_order_product`, `service_order_product`, `certificate_product`, `budget_products`, `budget_services`, `work_order_technicians`, `work_order_room`, `work_order_device`, `pest_sighting_items`), tabelas do Spatie, `migrations`, `sessions`, `cache`, `jobs`, `failed_jobs`, `password_reset_tokens`, `scheduled_task_runs`.

3. `MODELS_DE_DOMINIO: array<class-string>` -> models que precisam da trait `BelongsToCompany`. `User` entra na lista com nota: usa a trait para o preenchimento, mas o escopo global dele tem exceção (ver Task 4.6).

4. `UNIQUES_A_COMPOR: array` -> mapa `tabela => [nome_do_indice_atual, colunas]` das cinco uniques globais do `divida-tecnica.md`: `daily_cash_balances.balance_date`, `work_orders.order_number`, `service_orders.order_number`, `technicians.email`, `service_types.slug`. Mais qualquer outra unique global encontrada na varredura do schema, que **precisa ser reportada**, não silenciada.

5. Método `tabelaExiste(string $tabela): bool` usando `Schema::hasTable`, e método `conferir(): array` que devolve as divergências entre a lista declarada e o schema real (tabela declarada que não existe, tabela existente não classificada).

### Regras de negócio aplicáveis

- Toda tabela do banco precisa estar em uma das duas listas. Tabela não classificada é bug e o método `conferir()` a denuncia.
- Tabela pivot não recebe a coluna: o escopo chega pelo pai. Duplicar `company_id` na pivot cria caminho para divergência.
- `users.email` continua unique global de propósito (decisão registrada no PRD). Não entra em `UNIQUES_A_COMPOR`.
- Esta task não altera schema nem model algum. Só declara.

### Critérios de aceitação

- [ ] `DominioMultiempresa::conferir()` devolve array vazio no banco atual
- [ ] Toda tabela do schema aparece em exatamente uma das duas listas
- [ ] As cinco uniques do `divida-tecnica.md` estão em `UNIQUES_A_COMPOR`
- [ ] Uniques globais encontradas além das cinco estão listadas e reportadas no relatório da task
- [ ] Nenhuma migration nem model foi alterado
