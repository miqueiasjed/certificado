# Task 1.13 - Remover as tabelas órfãs

## Objetivo

Remover `work_order_products` e `service_order_products`, criadas por migration e nunca usadas pelo código, antes que a migração multiempresa do Plano 4 as trate como tabelas de domínio.

## Tipo

backend-estrutura

## Arquivos a criar/modificar

- `database/migrations/[timestamp]_drop_orphan_product_tables.php` -> criar

## Contexto necessário (ler antes)

- `.claude/prd/divida-tecnica.md` -> item 2
- `app/Models/WorkOrder.php:106` -> usa a pivot `work_order_product`, no singular
- `app/Models/ServiceOrder.php:58` -> usa a pivot `service_order_product`, no singular

- `database/migrations/2025_07_28_231026_create_service_order_products_table.php` -> estrutura a remover

## Skills necessárias

- `laravel-arquitetura`

## Especificação

### O que fazer

1. **Antes de escrever a migration**, confirmar que as tabelas estão realmente órfãs:
   ```
   grep -rn "work_order_products\|service_order_products" app/ database/seeders/ routes/ resources/
   ```
   O resultado só pode conter as próprias migrations de criação. Qualquer outra referência interrompe a task: relate e não remova nada.

2. Conferir que estão vazias no ambiente local:
   ```
   php artisan tinker --execute="dump(DB::table('work_order_products')->count(), DB::table('service_order_products')->count());"
   ```
   Registrar as duas contagens no retorno da task.

3. Criar a migration de remoção:
   - `up()`: `Schema::dropIfExists` nas duas tabelas, cada uma **precedida** de uma checagem de contagem. Se a tabela tiver qualquer linha, lançar `RuntimeException` com mensagem em português informando a tabela e a quantidade, abortando a migration.
   - `down()`: recriar as duas tabelas com a estrutura original das migrations de criação, para permitir voltar atrás.

4. Não apagar as migrations originais de criação. Histórico de migration não se reescreve em projeto que já rodou em produção.

### Regras de negócio aplicáveis

- **Produção ativa.** A migration precisa se recusar a apagar tabela com dado. A verificação de contagem dentro do `up()` é o que garante isso, já que a contagem no ambiente local não prova nada sobre produção.
- As pivots realmente usadas são `work_order_product` e `service_order_product`, no **singular**. Confundir singular com plural aqui apaga dado de OS em produção. Confira o nome caractere a caractere antes de escrever qualquer `dropIfExists`.
- Nenhum model, relacionamento ou Service é alterado nesta task.

### Critérios de aceitação

- [ ] A varredura por referências confirma que só as migrations de criação citam as tabelas
- [ ] As contagens das duas tabelas estão no retorno da task
- [ ] `php artisan migrate` remove as duas tabelas no ambiente local
- [ ] `php artisan migrate:rollback` recria as duas com a estrutura original
- [ ] As tabelas `work_order_product` e `service_order_product` (singular) continuam intactas, com o mesmo número de linhas de antes
- [ ] A migration aborta com exceção se encontrar linha em qualquer das duas tabelas

## Teste esperado

- Comando: `php artisan migrate` seguido de `php artisan migrate:rollback` e `php artisan migrate`
- Verificação manual: antes e depois, conferir `SELECT COUNT(*) FROM work_order_product` e `FROM service_order_product` (singular) e confirmar que o número não mudou
