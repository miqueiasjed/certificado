# Task 1.18 - A rotina só considera paga a parcela com data de pagamento

## Objetivo

Impedir que a rotina de status declare recebido um valor que não entrou. Hoje ela decide `paid` apenas por `amount_paid`, e o sistema cria parcelas **pendentes** com esse campo já preenchido.

## Tipo

backend-logica

## Arquivos a criar/modificar

- `app/Console/Commands/UpdatePaymentStatuses.php` -> modificar

## Contexto necessário (ler antes)

- `app/Console/Commands/UpdatePaymentStatuses.php` -> método `statusDaParcela()`
- `app/Http/Controllers/PaymentDetailController.php` -> por volta da linha 563, a criação da parcela pendente
- `app/Models/PaymentDetail.php` -> `scopePaid`, `scopePending`, e o accessor de status

## Por que esta task existe

`PaymentDetailController`, ao registrar um pagamento parcial, cria a parcela do valor restante assim:

```php
PaymentDetail::create([
    'payment_due_date' => now()->addDays(30)->toDateString(),
    'amount_paid' => $remainingAmount,   // valor A RECEBER
    'payment_status' => 'pending',
    // payment_date fica nulo
]);
```

`amount_paid` guarda ali o valor que ainda falta receber, e `payment_date` fica nulo. A regra da rotina é:

```php
return $valorPago >= $valorFinal ? 'paid' : 'partial';
```

Logo, ao rodar, a rotina reclassifica essa parcela pendente como `paid` ou `partial`. O resto do sistema trata `payment_date` preenchida como o sinal de pagamento: `statusDaOrdem()` soma com `whereNotNull('payment_date')`, e os scopes do model fazem o mesmo. A rotina é a única peça que discorda.

Existe registro nessa condição no banco local (parcela #4: `payment_date` nulo, `amount_paid` 100, status `paid`).

## Skills necessárias

- `laravel-arquitetura`
- `datas-timezone`

## Especificação

### O que fazer

1. Em `statusDaParcela()`, condicionar o ramo de pagamento à existência de `payment_date`:
   - `payment_date` nula -> a parcela não foi paga, independentemente de `amount_paid`. Decidir entre `pending` e `overdue` pelo vencimento, como a Task 1.17 estabeleceu.
   - `payment_date` preenchida -> aplicar a regra atual: `paid` quando o valor cobre o total, `partial` quando é menor.
2. Manter o critério de vencimento exatamente como a Task 1.17 deixou.
3. Garantir que o resultado concorde com `statusDaOrdem()`, que já soma apenas parcelas com `payment_date` preenchida.
4. Não alterar o controller nesta task. Corrigir a origem do dado e fazer o backfill dos registros já gravados é trabalho de outro plano, com etapa de conferência própria.

### Regras de negócio aplicáveis

- **Dinheiro.** Declarar como recebida uma parcela em aberto é o pior erro possível no painel financeiro do cliente. Na dúvida entre marcar pago e marcar pendente, marcar pendente.
- `payment_date` preenchida é o sinal de pagamento em todo o resto do sistema. A rotina passa a seguir a mesma convenção.
- Esta correção é defensiva: ela não conserta o dado já gravado errado, apenas impede que a rotina agendada piore o quadro.

### Critérios de aceitação

- [ ] Parcela com `amount_paid > 0` e `payment_date` nula não é classificada como `paid` nem como `partial`
- [ ] Essa mesma parcela recebe `pending` quando o vencimento é hoje ou futuro, e `overdue` quando já passou
- [ ] Parcela com `payment_date` preenchida e valor integral continua `paid`
- [ ] Parcela com `payment_date` preenchida e valor menor continua `partial`
- [ ] O status da parcela concorda com o que `statusDaOrdem()` calcula para a ordem correspondente
- [ ] `--dry-run` mostra quantas parcelas mudam de classificação por causa desta correção, incluindo o caso real do banco local
