# Task 1.14 - Testes de virada de dia e das rotinas

## Objetivo

Provar com teste automatizado que registro vencendo hoje não aparece vencido às 21h de Brasília, e que as rotinas agendadas registram cada rodada.

## Tipo

teste

## Arquivos a criar/modificar

- `tests/Unit/BusinessDateTest.php` -> criar
- `tests/Feature/RotinasAgendadasTest.php` -> criar

- `app/Console/Commands/UpdatePaymentStatuses.php` -> Task 1.6

## Especificação

### O que fazer

1. Se o banco `testing` não existir, criá-lo, ou ajustar `phpunit.xml` para SQLite em memória. Registrar no retorno da task qual caminho foi escolhido e por quê. Use `RefreshDatabase` nos testes de feature.

2. `BusinessDateTest` cobrindo:
   - `hoje()` devolve o dia de Brasília quando o horário do sistema é 02:00 UTC (que ainda é o dia anterior em Brasília). Use `Carbon::setTestNow()`
   - `estaVencido(hoje)` é `false`
   - `estaVencido(ontem)` é `true`
   - `estaVencido(amanhã)` é `false`
   - `estaVencido(null)` não lança exceção

3. `RotinasAgendadasTest` cobrindo:
   - **Virada de dia no certificado:** com `Carbon::setTestNow()` em `2026-07-26 00:30 UTC` (ou seja, 21:30 de 25/07 em Brasília), um certificado com `warranty = 2026-07-25` continua `active` após rodar `certificates:update-status`. Este é o teste central do plano
   - Certificado com `warranty` de ontem vira `expired`
   - Certificado `cancelled` não é tocado pela rotina
   - **Virada de dia no pagamento:** parcela com `payment_due_date` igual ao dia de Brasília não vira `overdue` rodando às 21:30 de Brasília
   - `--dry-run` não altera nenhum registro e o comando termina com sucesso
   - As quatro rotinas aparecem em `Schedule` (`php artisan schedule:list` ou a API do agendador) com o fuso do negócio
   - Rodar uma rotina agendada cria a linha correspondente em `scheduled_task_runs` com `status = 'success'`

4. Usar factories onde já existirem. Se não existir factory para `Certificate` ou `PaymentDetail`, criar apenas o mínimo necessário em `database/factories/`.

5. **Regras nascidas durante a execução do plano (Tasks 1.16, 1.17 e 1.18).** Cada uma corrigiu um bug que só apareceu porque a rotina passou a rodar. Todas precisam de teste que falhe se alguém reverter:

   - **Accessor concorda com a rotina (1.16):** com o tempo em 21h30 de Brasília, `Certificate::is_expired` é `false` e `calculated_status` é `active` para garantia que vence hoje. `days_until_expiry` devolve `0` para hoje e `0` quando não há garantia.
   - **Vencimento decide o atraso, não a data de pagamento (1.17):** parcela sem pagamento com `payment_due_date` futuro é `pending`, nunca `overdue`. Parcela sem `payment_due_date` é `pending`. Este teste protege contra marcar a carteira inteira como vencida.
   - **Valor sem data de pagamento não é recebimento (1.18):** parcela com `amount_paid > 0` e `payment_date` nula **não** pode virar `paid` nem `partial`. Ela segue o vencimento. Este é o teste que protege dinheiro: o sistema cria parcelas pendentes já com `amount_paid` preenchido.
   - **Acordo entre rotina e accessor:** para o mesmo registro, `PaymentDetail::payment_status` (com a coluna nula, forçando o ramo calculado) e o status que a rotina gravaria devem coincidir.

### Regras de negócio aplicáveis

- O teste de virada de dia é o critério de aceitação do plano inteiro. Ele precisa falhar se alguém reintroduzir `Carbon::today()` nas rotinas.
- Fixar o tempo com `Carbon::setTestNow()`, nunca depender do relógio real da máquina que roda a suíte.
- Teste não pode depender do fuso do sistema operacional: force o cenário pelo tempo fixado.

- [ ] Nenhum teste depende do fuso do sistema
