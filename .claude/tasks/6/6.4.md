# Task 6.4 - Middleware de módulo e aplicação nas rotas

## Objetivo

Negar no backend o acesso a rota de módulo inativo, com resposta clara, incluindo acesso direto por URL.

## Tipo

backend-endpoint

## Arquivos a criar/modificar

- `app/Http/Middleware/EnsureModuleIsActive.php` -> criar
- `bootstrap/app.php` -> modificar (alias `module`)
- `routes/web.php` -> modificar

## Contexto necessário (ler antes)

- `app/Services/ModuleService.php` -> criado na Task 6.3
- `routes/web.php` -> grupos de rota e middleware de permissão do Plano 2
- `app/Http/Middleware/EnsurePlatformAdmin.php` -> referência de middleware do projeto

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

1. `EnsureModuleIsActive` recebendo a chave do módulo como parâmetro (`module:financeiro`). Quando inativo:
   - requisição Inertia -> redireciona para uma página "Módulo indisponível" com o nome do módulo e o convite a conhecer o plano superior
   - requisição JSON -> 403 com `{'message': 'O módulo X não está disponível no seu plano.', 'modulo': 'chave'}`

2. Registrar o alias `module` em `bootstrap/app.php`.

3. Aplicar nas rotas, acumulando com o middleware de permissão do Plano 2 (os dois valem: permissão diz o que o usuário pode, módulo diz o que a empresa contratou):

   | Módulo | Rotas |
   |---|---|
   | `financeiro` | `/financial-dashboard`, `/cash-flow`, `/financial-entries`, `/financial-withdrawals`, `/payment-details`, `/daily-cash-balances` |
   | `contratos` | `/contracts`, `addresses.contracts.*`, `addresses.contract.pdf` |
   | `monitoramento` | rotas de relatório de monitoramento, quando existirem (Plano 21) |

   Os módulos ainda sem rota (`estoque`, `portal_cliente`, `app_tecnico`, `notificacoes`, `roteirizacao`, `nfse`, `laudo_ia`) ficam declarados no catálogo e ganham middleware quando o plano correspondente for implementado. Anotar isso no comentário do grupo, para o próximo plano não esquecer.

4. Rota da página "Módulo indisponível", fora de qualquer bloqueio de módulo.

### Regras de negócio aplicáveis

- A verificação vive no backend. Esconder o item de menu não impede digitar a URL, e essa é a regra explícita do PRD.
- Middleware de módulo e de permissão são independentes e ambos precisam passar. Usuário com `financeiro-ver` num tenant sem o módulo financeiro continua barrado.
- A mensagem diz qual módulo falta e convida ao plano superior. Erro 403 seco transforma oportunidade comercial em suporte.
- Toda rota financeira precisa ficar coberta. Rota financeira sem middleware é o mesmo furo que o Plano 2 fechou, com outra causa.

### Critérios de aceitação

- [ ] Tenant sem o módulo financeiro recebe a página de indisponível ao abrir `/financial-dashboard`
- [ ] O mesmo tenant recebe 403 com JSON claro em `/financial-entries/stats`
- [ ] Tenant com o módulo acessa normalmente
- [ ] Tenant interno acessa tudo
- [ ] Toda rota financeira listada tem o middleware
- [ ] `php artisan route:list` mostra os dois middlewares empilhados nas rotas financeiras

## Teste esperado

- Comando: `php artisan route:list --path=financial` e `php artisan test`
- Verificação manual: bloquear `financeiro` no tenant 1 em local e tentar as URLs à mão
