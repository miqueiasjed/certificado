# Task 6.5 - Limites quantitativos do plano

## Objetivo

Verificar os limites de usuários, clientes e OS por mês, avisar ao se aproximar do teto e nunca perder dado ao estourar.

## Tipo

backend-logica

## Arquivos a criar/modificar

- `app/Services/LimitesDoPlanoService.php` -> criar
- `app/Http/Middleware/HandleInertiaRequests.php` -> modificar (compartilhar avisos de limite)

## Contexto necessário (ler antes)

- `app/Models/Plan.php` -> campos de limite
- `app/Services/TenantUsageService.php` -> `usoAtual()`, criado na Task 5.6
- `app/Http/Middleware/HandleInertiaRequests.php` -> o que já é compartilhado
- `app/Support/BusinessDate.php` -> "OS do mês" depende do mês no fuso do negócio

## Skills necessárias

- `laravel-arquitetura`
- `datas-timezone`

## Especificação

### O que fazer

`LimitesDoPlanoService`:

1. `situacao(Company $empresa): array` -> por limite (`usuarios`, `clientes`, `os_mes`, `armazenamento_mb`): valor atual, teto, percentual, e estado (`ok`, `proximo`, `estourado`). `proximo` a partir de 80%.
2. `podeCriar(string $recurso, ?Company $empresa = null): bool` -> false só para `usuarios`, que é o único limite com bloqueio duro.
3. `avisos(Company $empresa): array` -> mensagens prontas para exibir, apenas dos limites em `proximo` ou `estourado`.
4. Compartilhar `avisos` no `HandleInertiaRequests::share()`, calculado de forma preguiçosa (`fn () => ...`), para não custar consulta em toda requisição de quem está longe do teto.

Aplicar `podeCriar('usuarios')` no Service de gestão de usuários (Plano 2, Task 2.12), recusando a criação com mensagem que nomeia o limite e o plano.

### Regras de negócio aplicáveis

- **Estourar limite nunca apaga nem esconde dado.** Cliente e OS acima do teto continuam funcionando; o que acontece é aviso, e a conversa comercial. Bloquear a operação de quem já pagou é pior que cobrar depois.
- Usuário é o único limite com bloqueio duro na criação, porque criar usuário é ato administrativo consciente, não fluxo de trabalho.
- Limite nulo é ilimitado: nenhuma verificação, nenhum aviso.
- "OS do mês" conta pelo mês corrente no fuso do negócio.
- Tenant interno tem todos os limites nulos pelo plano interno, sem regra especial no código.

### Critérios de aceitação

- [ ] `situacao()` devolve `proximo` a partir de 80% e `estourado` acima de 100%
- [ ] Limite nulo devolve estado `ok` e nenhum aviso
- [ ] Criar cliente acima do teto **funciona** e gera aviso
- [ ] Criar usuário acima do teto é recusado com mensagem que nomeia o limite
- [ ] Tenant interno não recebe aviso algum
- [ ] O cálculo de avisos não roda para quem está abaixo de 80%
