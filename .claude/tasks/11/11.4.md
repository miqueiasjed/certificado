# Task 11.4 - Endpoint de leitura do código com validação contra a OS

## Objetivo

Resolver um código lido e levar o técnico ao registro do dispositivo, avisando quando o dispositivo não pertence ao endereço da OS em execução.

## Tipo

backend-endpoint

## Arquivos a criar/modificar

- `app/Http/Controllers/DeviceScanController.php` -> criar
- `app/Services/DeviceScanService.php` -> criar
- `routes/web.php` -> modificar

## Contexto necessário (ler antes)

- `app/Http/Controllers/DeviceController.php` -> padrão de controller do projeto
- `app/Services/WorkOrderAccessService.php` -> como o técnico é restrito às próprias OS
- `app/Support/CodigoDeDispositivo.php` -> criado na Task 11.2
- `routes/web.php` -> grupo de rotas de dispositivo

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

1. `GET /dispositivos/ler/{codigo}` e `GET /api/dispositivos/ler/{codigo}` (versão JSON, consumida pelo leitor do frontend e depois pelo aplicativo do Plano 12). Parâmetro opcional `work_order_id`.

2. `DeviceScanService::resolver(string $codigo, ?int $workOrderId)` devolve um resultado com quatro situações possíveis:
   - `nao_encontrado`: código inválido no formato ou inexistente na empresa;
   - `fora_da_os`: dispositivo existe, mas o `address_id` dele não é o endereço da OS informada;
   - `substituido`: o dispositivo lido foi substituído, e o retorno aponta o dispositivo novo do mesmo ponto;
   - `ok`: dispositivo, endereço, tipo de isca e o último evento registrado.

3. O controller nunca resolve o `Device` por Model Binding pelo id: recebe o código e delega ao Service, que aplica o escopo da empresa. Código de outra empresa devolve `nao_encontrado`, com a mesma resposta de código inexistente.

4. Quando `work_order_id` vem preenchido, validar o acesso do usuário àquela OS pelo `WorkOrderAccessService` antes de qualquer comparação. Técnico que não é dono da OS recebe 403.

5. Registrar a leitura não é escopo desta task. O registro do evento pelo aplicativo entra no Plano 13.

### Regras de negócio aplicáveis

- `fora_da_os` é **aviso, não bloqueio**: o técnico pode estar conferindo um ponto do endereço vizinho de propósito. O que não pode é registrar no lugar errado em silêncio, então a resposta traz o endereço real do dispositivo lido para ele decidir.
- Código de outra empresa e código inexistente devolvem exatamente a mesma resposta. Diferenciar as duas respostas permite descobrir quais códigos existem na plataforma.
- O caso `substituido` existe porque a etiqueta antiga continua colada no local até alguém trocar. Ler etiqueta antiga precisa levar ao dispositivo atual do ponto, não a um erro.
- Rota de leitura exige autenticação. Não é rota pública.

### Critérios de aceitação

- [ ] Ler um código válido do próprio endereço da OS devolve `ok` com o dispositivo
- [ ] Ler um código de outro endereço devolve `fora_da_os` com o endereço real
- [ ] Ler um código de outra empresa devolve `nao_encontrado`
- [ ] Ler o código de um dispositivo substituído aponta o dispositivo novo
- [ ] Técnico que não é dono da OS recebe 403 ao informar `work_order_id`
- [ ] Código malformado não chega a consultar o banco
