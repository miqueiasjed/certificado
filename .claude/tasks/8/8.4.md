# Task 8.4 - Service e endpoints de convite de usuário

## Objetivo

Convidar um usuário para a empresa com papel definido no convite, e permitir que ele crie a própria senha por um link com validade.

## Tipo

backend-endpoint

## Arquivos a criar/modificar

- `app/Services/InvitationService.php` -> criar
- `app/Http/Controllers/InvitationController.php` -> criar
- `routes/web.php` -> modificar

## Contexto necessário (ler antes)

- `app/Models/Invitation.php` -> criado na Task 8.1
- `app/Services/UserService.php` -> criado no Plano 2 (Task 2.12), regra de criação de usuário
- `app/Services/LimitesDoPlanoService.php` -> `podeCriar('usuarios')`, do Plano 6
- `routes/web.php` -> grupos e middleware

## Especificação

### O que fazer

1. `InvitationService`:
   - `convidar(Company $empresa, string $email, string $papel, ?string $nome, User $convidadoPor): Invitation` -> recusa se já houver usuário com esse e-mail, se houver convite pendente para o mesmo e-mail na mesma empresa, ou se o limite de usuários do plano estiver estourado
   - `aceitar(string $token, string $nome, string $senha): User` -> valida token, validade e estado, cria o usuário com `company_id` da empresa do convite e o papel do convite, marca `aceito_em`
   - `cancelar(Invitation $convite): void`
   - `reenviar(Invitation $convite): Invitation` -> gera token novo e estende a validade
   - Validade padrão de 7 dias, contada por dia no fuso do negócio

2. `InvitationController`:
   - `store`, `destroy` e `reenviar` -> dentro do grupo autenticado, exigindo `usuario-criar`
   - `show` (GET `/convite/{token}`) e `aceitar` (POST) -> **públicos**, sem autenticação

3. Envio do e-mail: a central de notificações é o Plano 14. Enquanto ela não existir, usar o `Mail` do Laravel com um Mailable simples, e deixar anotado o ponto de troca. Se o envio falhar, o convite continua gravado e o link pode ser copiado da tela (Task 8.8).

### Regras de negócio aplicáveis

- O papel vem do convite e não é escolhido por quem aceita. Deixar o convidado escolher o próprio papel entrega administrador para qualquer um.
- Aceitar convite expirado, já aceito ou cancelado devolve mensagem clara, sem revelar se o e-mail existe no sistema.
- Token é de uso único: aceito, não serve mais.
- O usuário criado nasce no `company_id` da empresa do convite, nunca no tenant da requisição, que é nulo por ser rota pública.
- Limite de usuários do plano bloqueia o convite na origem, não no aceite. Deixar convidar e recusar no fim é pior experiência.

### Critérios de aceitação

- [ ] Convidar cria o registro e envia o e-mail
- [ ] Convidar e-mail já cadastrado é recusado com mensagem
- [ ] Convite pendente duplicado é recusado
- [ ] Limite de usuários estourado impede o convite
- [ ] Aceitar cria o usuário com o papel e a empresa do convite
- [ ] Token expirado, já usado ou cancelado é recusado
- [ ] As rotas de aceite funcionam sem autenticação
- [ ] Falha de e-mail não impede a criação do convite
