# Task 8.3 - Service de provisionamento do tenant

## Objetivo

Criar o passo que deixa um tenant recém-criado pronto para operar: cadastros semeados, trilha iniciada e administrador com papel.

## Tipo

backend-logica

## Arquivos a criar/modificar

- `app/Services/ProvisionamentoService.php` -> criar

## Contexto necessário (ler antes)

- `app/Services/TenantService.php` -> `criar()`, criado na Task 5.4
- `app/Support/CatalogoInicialDoTenant.php` -> criado na Task 8.2
- `app/Support/TenantAtual.php` -> `comTenant()`
- `database/seeders/RolesAndPermissionsSeeder.php` -> papéis do Plano 2

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

`ProvisionamentoService`:

1. `provisionar(Company $empresa, array $dadosDoAdministrador): User` -> executa, dentro de `TenantAtual::comTenant($empresa->id, ...)` e em transação:
   - cria o usuário administrador e atribui o papel `administrador`
   - aplica o catálogo inicial (Task 8.2)
   - cria os passos da trilha (Task 8.5) com estado pendente
   - devolve o administrador criado

2. `reprovisionarCadastros(Company $empresa): array` -> reaplica só o catálogo, para o caso de um tenant antigo que ficou sem algum cadastro. Idempotente.

3. `TenantService::criar()` passa a chamar `provisionar()` no lugar da criação solta do administrador que ele faz hoje.

4. Falha em qualquer passo desfaz tudo: tenant meio provisionado é pior que tenant inexistente, porque parece pronto e não é.

### Regras de negócio aplicáveis

- Papéis e permissões são globais (Spatie sem `teams`, decisão do Plano 2). O administrador do tenant novo recebe o papel `administrador`, que já existe. Nenhum papel é criado por tenant.
- Todo dado semeado nasce com o `company_id` do tenant novo, garantido pelo `comTenant()` mais a trait do Plano 4.
- Provisionamento é idempotente no que diz respeito ao catálogo: reexecutar não duplica cadastro.
- Nenhum e-mail é enviado aqui. O convite é a Task 8.4.

### Critérios de aceitação

- [ ] `provisionar()` cria administrador, catálogo e trilha em uma transação
- [ ] Falha no meio não deixa nada gravado
- [ ] Todo registro criado tem o `company_id` do tenant novo
- [ ] O administrador recebe o papel `administrador`
- [ ] `reprovisionarCadastros()` em tenant já provisionado não duplica nada
- [ ] `TenantService::criar()` usa este Service
