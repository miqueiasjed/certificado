# Task 30.4 - Agenda mescla ordens de serviço e compromissos

## Objetivo

Fazer `/agenda/dados` devolver, num único período consultado, tanto as ordens
de serviço quanto os compromissos avulsos, cada item identificável por tipo.

## Tipo

backend-logica

## Arquivos a criar/modificar

- `app/Services/AgendaService.php` -> modificar
- `app/Http/Controllers/AgendaController.php` -> modificar

## Contexto necessário (ler antes)

  `formatar()` são o que muda

## Especificação

### O que fazer

1. `AgendaService::doPeriodo()` passa a aceitar um segundo builder de
   entrada, para compromissos, além do já existente para ordens de serviço:

   ```php
   public function doPeriodo(
       string $inicio,
       string $fim,
       array $filtros = [],
       ?Builder $consultaDeOs = null,
       ?Builder $consultaDeCompromissos = null,
   ): array
   ```

   Mantém compatibilidade: quando `$consultaDeCompromissos` não é informado,
   parte de `Compromisso::query()` sem escopo adicional (mesmo critério já
   usado para `$consulta`/OS).

2. Cada compromisso do período é formatado num shape compatível com o que o
   calendário já espera de uma "visita" — reaproveitar os MESMOS nomes de
   campo do item de OS sempre que o conceito for o mesmo (`cliente`,
   `endereco`, `cidade`, `tecnico`, `sem_tecnico`, `data`, `hora_inicio`,
   `hora_fim`), e acrescentar um discriminador novo em **todo** item
   devolvido (OS incluída): `'tipo_item' => 'os'` ou `'tipo_item' =>
   'compromisso'`. Para compromisso, o campo equivalente a `status`/
   `status_texto` de OS é `situacao` (`agendado`/`concluido`/`cancelado`) com
   um rótulo em português.

3. `doPeriodo()` mescla as duas coleções formatadas, ordena por `data` e
   depois por `hora_inicio` (nulls por último, mesmo critério do
   `orderBy('start_time')` atual), e devolve a lista única.

4. Filtro de situação: compromisso cancelado some por padrão do mesmo jeito
   que OS cancelada (`SITUACAO_OCULTA_POR_PADRAO`), e volta a aparecer se o
   filtro de `status` pedir explicitamente. `service_id` e `cidade` (quando
   vem de endereço) só filtram OS: compromisso sem `address_id` (endereço em
   texto livre) não participa do filtro por cidade; decida e documente no
   código a regra escolhida (sugestão: compromisso sem endereço cadastrado
   simplesmente não aparece quando o filtro de cidade está ativo, mesmo
   critério de "sem dado, sem match").

5. `AgendaController::dados()`: monta a segunda query,
   `Compromisso::query()`, aplicando o mesmo filtro de técnico do usuário
   autenticado (papel `tecnico` só vê os compromissos onde
   `technician_id` é o dele; sem cadastro de técnico vinculado, vê zero,
   mesmo critério de `WorkOrderAccessService`), e passa as duas queries para
   `doPeriodo()`.

### Regras de negócio aplicáveis

- Técnico autenticado só enxerga os próprios compromissos, mesmo critério
  já aplicado às ordens de serviço.
- Nenhuma mudança no formato que o frontend já consome para item de OS além
  do campo novo `tipo_item` — é aditivo, não quebra o que já funciona.
- Sem conversão de fuso na formatação: usar `BusinessDate` como o resto do
  arquivo já faz.

### Critérios de aceitação

- [ ] `doPeriodo()` devolve OS e compromissos juntos, ordenados
- [ ] Toda linha devolvida (OS e compromisso) tem `tipo_item`
- [ ] Técnico autenticado só recebe os próprios compromissos
- [ ] Compromisso cancelado não aparece sem o filtro de situação pedir
- [ ] Sem compromisso nenhum no período, a resposta é idêntica à de hoje
      (só as OS)
