# Task 30.2 - CompromissoService: ciclo de vida e promoção para OS

## Objetivo

Concentrar toda regra de negócio do compromisso avulso: criar, atualizar,
cancelar, concluir e, quando fizer sentido, promover para uma Ordem de
Serviço de verdade.

## Especificação

### O que fazer

1. `CompromissoService::criar(array $dados): Compromisso` - cria o registro.
   `$dados['criado_por']` já vem resolvido por quem chama (o controller passa
   `Auth::id()`); o Service nunca chama `Auth::user()` internamente, mesmo
   critério do `PpeDeliveryController`/`PpeDeliveryService` (roda fora de
   requisição HTTP também, ex.: comando artisan futuro).

2. `CompromissoService::atualizar(Compromisso $compromisso, array $dados):
   Compromisso` - atualiza os campos editáveis. Compromisso já promovido
   (`work_order_id` preenchido) continua editável: editar o compromisso não
   mexe na OS gerada, são dois registros independentes a partir da promoção.

3. `CompromissoService::cancelar(Compromisso $compromisso): Compromisso` -
   seta `situacao = 'cancelado'`. Recusa cancelar compromisso já concluído
   (lança `CompromissoNaoPromovelException` não se aplica aqui: usar uma
   `RuntimeException` de domínio própria só se o projeto pedir; **decisão
   default para esta task: cancelar um compromisso concluído é permitido**,
   é o mesmo espírito de "cancelada nunca some, só muda de situação" já usado
   em outras partes do domínio. Não adicionar bloqueio que o plano não pediu.

4. `CompromissoService::concluir(Compromisso $compromisso): Compromisso` -
   seta `situacao = 'concluido'`.

5. `CompromissoService::promoverParaOs(Compromisso $compromisso, array
   $dadosAdicionais = []): WorkOrder` - monta os dados da OS a partir do
   próprio compromisso (cliente, endereço, técnico, data) mesclados com
   `$dadosAdicionais` (o que falta para uma OS válida e o compromisso não
   tem, ex.: `service_id`), chama `WorkOrderService::createWorkOrder()`, e
   grava `work_order_id` no compromisso **sem apagar nenhum outro campo**.
   Recusa promover quando:
   - o compromisso já tem `work_order_id` preenchido (já foi promovido);
   - `situacao === 'cancelado'`.

   As duas recusas lançam `CompromissoNaoPromovelException`, com mensagem
   pronta em português e o motivo específico (já promovido vs. cancelado),
   mesmo padrão de `EpiComEntregaException`.

### Regras de negócio aplicáveis

- A promoção é sempre opcional: um compromisso que nunca vira OS continua
  válido para sempre. Nada neste Service torna a promoção obrigatória.
- `criado_por` e qualquer outro dado de quem-fez-o-quê chega de fora, nunca
  resolvido com `Auth::` dentro do Service.
- Nenhuma chamada a `WorkOrderService::createWorkOrder()` fora de
  `promoverParaOs()`.

### Critérios de aceitação

- [ ] `criar()`, `atualizar()`, `cancelar()`, `concluir()` e
      `promoverParaOs()` implementados e testáveis isoladamente (sem HTTP)
- [ ] Promover compromisso já promovido lança
      `CompromissoNaoPromovelException` com mensagem em português
- [ ] Promover compromisso cancelado lança a mesma exceção, mensagem
      distinta
- [ ] Depois de `promoverParaOs()`, o compromisso continua com todos os
      próprios dados intactos, só `work_order_id` muda
