# Task 25.2 - Provedor de IA com isolamento por tenant

## Objetivo

Isolar o modelo atrás de uma interface própria, montando o contexto apenas com dado do próprio tenant.

## Tipo

backend-logica

## Especificação

### O que fazer

1. Instalar o SDK oficial: `composer require anthropic-ai/sdk`. Chave em `config/ai.php`, lida de variável de ambiente, **nunca** por tenant: a conta é da plataforma, e o custo é medido por tenant na Task 25.5.

2. Interface `ProvedorDeTexto` com `gerar(string $sistema, string $entrada, array $opcoes = []): RespostaDeTexto`, devolvendo texto, tokens de entrada, tokens de saída, tokens lidos do cache e o identificador do modelo. Trocar de provedor depois não deve tocar em nada acima dessa interface.

3. `ProvedorAnthropic`: usa `claude-opus-5` como padrão, configurável em `config/ai.php`. Detalhes que evitam erro na integração:
   - parâmetros nomeados em camelCase no SDK PHP (`maxTokens`);
   - **não enviar** `temperature`, `topP` nem `topK`: são recusados com 400 neste modelo;
   - `maxTokens` de 4096 é suficiente para parecer técnico; usar streaming apenas se algum uso passar de 16000;
   - registrar `usage` da resposta (entrada, saída e `cache_read_input_tokens`).

4. Cache de prefixo: o prompt de sistema (instruções do parecer, vocabulário técnico do setor, formato esperado) é **estável** e leva `cacheControl` do tipo `ephemeral`; o dado da OS entra depois, na mensagem do usuário. Isso corta a maior parte do custo, já que o prefixo se repete em toda geração. O prefixo precisa ser byte a byte idêntico entre chamadas: nada de data, nome do tenant ou identificador interpolado nele.

5. `MontadorDeContexto::paraOs(WorkOrder $os): string`: monta o texto de entrada apenas com dados da OS: produtos aplicados com quantidade, pragas encontradas, dispositivos com ocorrência, adequações recomendadas, cômodos tratados e data. **Nenhum dado de outro tenant e nenhum dado de outro cliente entra no contexto**, nem como exemplo.

6. Tratamento de erro: limite de taxa, indisponibilidade e recusa do modelo viram exceções de domínio distintas, com mensagem em português. Toda tentativa grava `AiUsage`, inclusive a que falhou.

### Regras de negócio aplicáveis

- Isolamento por tenant é a regra central do plano: nenhum dado de uma empresa alimenta a sugestão de outra. Um exemplo de outro cliente colado no prompt já é vazamento.
- O prefixo estável e cacheado é o que torna o custo viável. Interpolar qualquer coisa variável nele invalida o cache e multiplica a conta.
- Sem `temperature`: o modelo em uso recusa o parâmetro, e a variação de estilo, quando desejada, vem da instrução no prompt.
- Chave de API nunca em log, nunca no banco, nunca devolvida por endpoint.

### Critérios de aceitação

- [ ] A interface cobre geração e devolve os tokens usados
- [ ] O modelo padrão vem da configuração
- [ ] Nenhum parâmetro de amostragem é enviado
- [ ] O prefixo cacheado é idêntico entre duas chamadas seguidas (afirmar `cache_read_input_tokens > 0` na segunda)
- [ ] O contexto montado não contém dado de outro tenant nem de outro cliente
- [ ] Falha grava `AiUsage` com `sucesso = false` e o motivo
- [ ] A chave não aparece em log
