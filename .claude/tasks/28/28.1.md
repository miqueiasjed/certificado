## Especificação

### O que fazer

1. **`personal_protective_equipments`** — o modelo de EPI que a empresa compra:

   | Coluna | Tipo | Observação |
   |---|---|---|
   | `company_id` | FK | escopo global, como todo model de domínio |
   | `nome` | string | "Respirador semifacial 3M 6200" |
   | `tipo` | enum | `respirador`, `luva`, `oculos`, `protetor_auricular`, `calcado`, `vestimenta`, `outro` |
   | `fabricante` | string nullable | |
   | `numero_ca` | string nullable | número do Certificado de Aprovação |
   | `validade_ca` | date nullable | validade **do certificado** |
   | `vida_util_dias` | integer nullable | prazo padrão de troca do item entregue |
   | `obrigatorio` | boolean, default `false` | usado pelo Plano 29 |
   | `ativo` | boolean, default `true` | |
   | `observacoes` | text nullable | |

   `numero_ca` e `validade_ca` nascem **nullable** de propósito: o tenant cadastra
   o EPI antes de ter o certificado em mãos, e campo em branco nunca é
   irregularidade — é a mesma regra do cadastro regulatório do Plano 24. Unique
   composto de `company_id` + `numero_ca` **não** deve ser criado: dois modelos de
   EPI diferentes podem compartilhar CA (mesmo certificado, tamanhos distintos).

2. **`ppe_deliveries`** — a ficha, uma linha por item entregue:

   | Coluna | Tipo | Observação |
   |---|---|---|
   | `company_id` | FK | |
   | `technician_id` | FK | quem recebeu |
   | `personal_protective_equipment_id` | FK | o que recebeu |
   | `quantidade` | integer, default 1 | |
   | `entregue_em` | date | dia da entrega no fuso do negócio |
   | `motivo` | enum | `primeira_entrega`, `substituicao`, `dano`, `perda`, `vencimento`, `outro` |
   | `numero_ca` | string nullable | **cópia** do CA no momento da entrega |
   | `validade_ca` | date nullable | **cópia** da validade no momento da entrega |
   | `trocar_ate` | date nullable | calculado de `vida_util_dias` na 28.2 |
   | `assinatura_path` | string nullable | imagem da assinatura de recebimento |
   | `assinado_em` | datetime nullable | instante da assinatura |
   | `devolvido_em` | date nullable | |
   | `motivo_devolucao` | string nullable | |
   | `estornada_em` | datetime nullable | ver regra 2 abaixo |
   | `motivo_estorno` | text nullable | |
   | `user_id` | FK nullable | quem registrou |

   Índice em (`company_id`, `technician_id`, `entregue_em`) — a ficha do técnico
   é a consulta principal e a extração da 28.5 varre por período.

3. Nos models: `BelongsToCompany` nos dois; `Auditavel` **em `PpeDelivery`**,
   porque estorno e devolução precisam deixar rastro de quem alterou.

4. Casts: `validade_ca`, `entregue_em`, `trocar_ate`, `devolvido_em` como `date`
   (dia sem hora, nunca sofre conversão de fuso); `assinado_em` e `estornada_em`
   como `datetime` (instante, gravado em UTC).

5. Constantes de classe `TIPOS` e `MOTIVOS` iguais aos enums, no padrão de
   `VehicleDocument::TIPOS` e `StockMovement::TIPOS`.

6. Docblock em cada model explicando **a decisão**, não o óbvio: por que o CA é
   copiado, por que a entrega não se edita, por que as duas validades são
   colunas separadas.

### Regras de negócio aplicáveis

- **As duas validades são independentes.** `validade_ca` é do certificado do
  fabricante e vale para as entregas futuras daquele modelo. `trocar_ate` é do
  item que aquele técnico tem na mão. Renovar um não mexe no outro. Esta é a
  decisão central do plano — está em `.claude/prd/seguranca-do-trabalho.md`.
- **A entrega é imutável.** Documento oponível, arquivado por 20 anos. Não existe
  edição nem exclusão: erro vira `estornada_em` + `motivo_estorno`, na mesma
  convenção do movimento de ajuste do razão de estoque do Plano 17.
- Migration é **aditiva**: só cria tabelas novas, nenhuma coluna em tabela com
  dado em produção. Não precisa de aplicação em etapas.
- `down()` derruba apenas as duas tabelas novas. Nenhum `DROP COLUMN` em tabela
  existente — o `down()` destrutivo do Plano 27 é o que não se deve repetir.
