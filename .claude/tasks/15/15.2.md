# Task 15.2 - Autenticação do cliente: convite, senha e recuperação

## Objetivo

Permitir que a empresa convide o cliente e que ele defina senha, entre e recupere o acesso, tudo separado do login dos funcionários.

## Tipo

backend-logica

## Arquivos a criar/modificar

- `app/Services/ClientUserService.php` -> criar
- `app/Http/Controllers/Portal/PortalAuthController.php` -> criar
- `app/Http/Middleware/AutenticarCliente.php` -> criar
- `routes/portal.php` -> criar

## Contexto necessário (ler antes)

- `app/Models/ClientUser.php` -> criado na Task 15.1
- `app/Http/Controllers/AuthController.php` -> fluxo de login atual dos funcionários
- `app/Services/NotificationService.php` -> convite e recuperação saem pela central do Plano 14
- `bootstrap/app.php` -> registro de rotas e middleware

## Skills necessárias

- `laravel-arquitetura`
- `permissoes-e-multitenancy`

## Especificação

### O que fazer

1. `ClientUserService`:
   - `convidar(Client $cliente, array $dados)`: cria o acesso, gera token de 64 caracteres com validade de 7 dias e enfileira o evento `convite_portal` na central de notificações;
   - `definirSenha(string $token, string $senha)`: valida o token e a validade, grava a senha, marca `email_verificado_em` e invalida o token;
   - `reenviarConvite`, `desativar`, `reativar`.

2. `PortalAuthController`: login, logout, esqueci a senha e redefinir, todos no guard `cliente`. Limite de 5 tentativas de login por minuto por e-mail e por IP.

3. Middleware `AutenticarCliente`: exige o guard `cliente`, resolve o tenant a partir de `client_users.company_id` (nunca do domínio nem de parâmetro de URL) e recusa acesso quando o cliente ou o acesso estiver inativo.

4. Arquivo de rotas próprio `routes/portal.php`, com prefixo `/portal`, registrado em `bootstrap/app.php`. Separar o arquivo é o que torna possível revisar de uma vez tudo que o cliente externo alcança.

5. Mensagem de erro de login idêntica para senha errada, e-mail inexistente e conta inativa. Diferenciar permite descobrir quem é cliente de quem.

### Regras de negócio aplicáveis

- O tenant do cliente vem do registro dele, nunca da URL. Aceitar `company_id` por parâmetro é o caminho mais direto para vazamento entre empresas.
- Token de convite expira em 7 dias e é de uso único. Link de convite eterno circulando em e-mail encaminhado é acesso permanente sem controle.
- O cliente nunca alcança rota do sistema interno, e o funcionário nunca entra pelo portal. Guards distintos, arquivos de rota distintos.
- Desativar o cliente derruba o acesso na requisição seguinte, sem esperar a sessão expirar.

### Critérios de aceitação

- [ ] Convidar cria o acesso e envia o e-mail com o link
- [ ] Definir senha por token válido funciona uma vez
- [ ] Token expirado ou reutilizado é recusado
- [ ] Login com senha errada, e-mail inexistente e conta inativa devolvem a mesma mensagem
- [ ] Seis tentativas em um minuto devolvem 429
- [ ] Cliente autenticado não alcança nenhuma rota de `routes/web.php`
- [ ] Funcionário autenticado não alcança `/portal`
- [ ] Desativar o acesso derruba na requisição seguinte
