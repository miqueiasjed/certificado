## Especificação

### Contrato de reordenação mista (decisão desta task, coordenar com 31.2)

O corpo de `PUT /roteiros/{route}/ordem` deixa de ser `work_order_ids:
[int]` e passa a ser `paradas: [string]`, cada item no formato
`"os:{id}"` ou `"compromisso:{id}"` (ex.: `["os:12", "compromisso:5",
"os:7"]`). Motivo do formato: mantém o corpo um array plano de strings, mais
simples de montar no frontend (arrastar e soltar cartões que já sabem o
próprio tipo e id) do que uma lista de objetos, e mais simples de validar
com uma regra de formato só.

`RouteService::reordenarManualmente()` (Task 31.2) precisa aceitar essa
mesma lista de strings e fazer o `keyBy` das paradas atuais por uma chave
composta equivalente (`"os:{work_order_id}"` /
`"compromisso:{compromisso_id}"`), para o `diff` de conferência (a lista
precisa bater exatamente com as paradas atuais) continuar funcionando. Se a
Task 31.2 já tiver sido concluída com um contrato diferente, ajustar esta
task para o contrato real em vez de duplicar a decisão.

### O que fazer

1. **`ReordenarRotaRequest`**: regra nova para `paradas` (`required|array|
   min:1`) e `paradas.*` (`required|string|regex:/^(os|compromisso):\d+$/`).
   Mensagens em português equivalentes às que já existem para
   `work_order_ids`.

2. **`RouteController::ordem()`**: troca `$request->validated('work_order_ids')`
   por `$request->validated('paradas')`, repassado direto para
   `RouteService::reordenarManualmente()`.

3. **`RouteController::apresentarRota()`**: o `map()` sobre `$rota->stops`
   passa a ramificar por `$parada->eDeCompromisso()`:
   - `loadMissing()` ganha `stops.compromisso.address`,
     `stops.compromisso.client` (ao lado do que já carrega para
     `stops.workOrder.*`).
   - Cada item do array `paradas` ganha `'tipo_item' => 'os'` ou
     `'tipo_item' => 'compromisso'` (mesmo nome de discriminador já usado em
     `AgendaService::doPeriodo()`, Task 30.4, para o frontend não aprender
     dois vocabulários diferentes).
   - Para compromisso: `cliente` vem de `$compromisso->client?->name`
     (`null` quando não há cliente vinculado, compromisso mostra `titulo`
     no lugar), `endereco` vem de `$compromisso->address?->full_address` ou,
     na ausência de endereço cadastrado, `$compromisso->endereco_texto`;
     `latitude`/`longitude`/`precisao_geocodificacao` só existem quando há
     `address_id`. Acrescentar também `'compromisso_titulo' =>
     $compromisso->titulo` e `'compromisso_tipo' => $compromisso->tipo`,
     para o frontend (Task 31.4) não precisar de uma segunda consulta para
     mostrar o cartão.
   - `route_stop_id`, `ordem`, `chegada_estimada`,
     `distancia_anterior_km`, `duracao_anterior_min` continuam iguais nos
     dois casos: são campos da própria `RouteStop`, não da origem.

### Regras de negócio aplicáveis

- `{route}` continua chegando por route-model binding escopado: roteiro de
  outra empresa não é encontrado, 404.
- A reordenação continua exigindo que a lista bata exatamente com as
  paradas atuais do roteiro (regra já em `RouteService`, Task 31.2): esta
  task só muda o formato do identificador, não a regra de conferência.

### Critérios de aceitação

- [ ] `GET /roteiros`, `POST /roteiros/otimizar`, `GET /roteiros/{route}/mapa`
      e `GET /api/app/roteiro` devolvem parada de compromisso com
      `tipo_item`, `compromisso_titulo` e `compromisso_tipo`
- [ ] `PUT /roteiros/{route}/ordem` aceita lista mista de `"os:N"` e
      `"compromisso:N"` e reordena as duas
- [ ] Formato antigo (`work_order_ids`) não é mais aceito: o `FormRequest`
      recusa corpo sem `paradas`
- [ ] Roteiro só com OS continua respondendo exatamente como antes (nenhuma
      regressão de campo)
