## Especificação

### O que fazer

O formato de "parada" que circula dentro da classe (o array que
`osAgendadasDoDia()`/`paradasDasOrdens()` produzem e que
`OtimizadorDeRota::ordenar()` consome e devolve) ganha duas chaves no lugar
de uma:

```php
array{
    work_order_id: ?int,
    compromisso_id: ?int,
    coordenada: ?Coordenada,
    precisao_geocodificacao: ?string,
    ancorada: bool,
    horario_ancora: ?string,
}
```

Exatamente um dos dois ids preenchido por parada, nunca os dois, nunca
nenhum. `OtimizadorDeRota::ordenar()` **não muda**: ele só ecoa `$parada +
[...]`, então continua funcionando com a chave nova sem tocar em nada além
do docblock (item 8).

1. **Nova consulta irmã de `osAgendadasDoDia()`**:
   ```php
   private function compromissosAgendadosDoDia(Technician $tecnico, string $dia): Collection
   {
       return Compromisso::query()
           ->with('address')
           ->where('technician_id', $tecnico->id)
           ->whereDate('data', $dia)
           ->where('situacao', 'agendado')
           ->orderBy('id')
           ->get();
   }
   ```
   Só `situacao = 'agendado'` entra: compromisso concluído já aconteceu, não
   precisa de deslocamento a planejar; cancelado não vai acontecer. Mesmo
   filtro de `SITUACOES_AGENDADAS` para OS, adaptado ao catálogo de
   `Compromisso::SITUACOES`.

2. **`paradasDasOrdens()` continua só para OS.** Nova função irmã,
   `paradasDosCompromissos(Collection $compromissos): array`, mesmo formato
   de saída, lendo `$compromisso->address` (nunca `endereco_texto`:
   compromisso sem `address_id` não tem coordenada, mesmo tratamento que OS
   sem endereço geocodificado já recebe) e `$compromisso->hora_inicio` como
   equivalente de `$ordem->start_time` (presença de `hora_inicio` é o sinal
   de "horário combinado", mesmo critério documentado no cabeçalho da classe
   para OS).

3. **`montar()` e `simularOtimizacao()`**: em cada um, depois de buscar
   `$ordens = $this->osAgendadasDoDia(...)`, buscar também `$compromissos =
   $this->compromissosAgendadosDoDia(...)`, montar `$paradas =
   array_merge($this->paradasDasOrdens($ordens),
   $this->paradasDosCompromissos($compromissos))`, e seguir o fluxo já
   existente (`$this->otimizador->ordenar($paradas, $partida)`) sem mais
   mudança nesses dois métodos além disso.

4. **`gravarParadas()`**: a chave de `updateOrCreate()` passa a ser as três
   colunas:
   ```php
   RouteStop::query()->updateOrCreate(
       [
           'route_id' => $rota->id,
           'work_order_id' => $parada['work_order_id'],
           'compromisso_id' => $parada['compromisso_id'],
       ],
       [...]
   );
   ```
   Como exatamente um dos dois é sempre `null` por parada, esta chave
   encontra a linha certa nos dois casos (Eloquent traduz `null` em
   `whereNull`). O resto do método (cálculo de distância/duração,
   `whereNotIn('id', $idsMantidos)->delete()`) não muda.

5. **`sincronizarPreservandoOrdemManual()`**: hoje decide o que remover e o
   que é novo comparando só `$parada->work_order_id` contra
   `$ordens->keyBy('id')`. Passa a comparar as duas origens:
   ```php
   $compromissos = $this->compromissosAgendadosDoDia($tecnico, $dia)->keyBy('id');
   // ...
   $aindaNoDia = fn (RouteStop $parada): bool => $parada->eDeCompromisso()
       ? $compromissos->has($parada->compromisso_id)
       : $ordens->has($parada->work_order_id);
   ```
   E o bloco que cria parada nova para o que "sobrou de fora" percorre as
   duas coleções (OS novas E compromissos novos), cada um criando com a
   coluna certa preenchida e a outra `null`.

6. **`recalcularDistancias()`**: `$rota->stops()->with('workOrder.address')`
   vira `->with(['workOrder.address', 'compromisso.address'])`, e a
   resolução do endereço passa a ser:
   ```php
   $endereco = $parada->eDeCompromisso() ? $parada->compromisso?->address : $parada->workOrder?->address;
   ```
   Resto do método (cálculo de distância a partir da coordenada) não muda.

7. **`chegadaEstimada()`**: `$rota->stops()->with('workOrder')` vira
   `->with(['workOrder', 'compromisso'])`, e a leitura do "horário
   combinado" passa a ser:
   ```php
   $horarioCombinado = $parada->eDeCompromisso() ? $parada->compromisso?->hora_inicio : $parada->workOrder?->start_time;
   ```
   Resto do método (avanço do relógio simulado) não muda.

8. **`OtimizadorDeRota.php`**: atualizar só os três docblocks (linhas ~28,
   94, 95) que hoje descrevem `work_order_id: int` como identificador único
   da parada, para `work_order_id: ?int` + `compromisso_id: ?int`, mantendo
   a explicação de que o método é agnóstico ao conteúdo dessas duas chaves.
   Nenhuma linha de código muda neste arquivo.

### Regras de negócio aplicáveis

- Exatamente um vínculo por parada (`work_order_id` xor `compromisso_id`) é
  regra deste Service, nunca do banco (o projeto não usa `CHECK` de banco
  para regra de negócio, mesmo critério já registrado na migration da Task
  de schema).
- Compromisso `cancelado` nunca entra no roteiro (equivalente a OS
  `cancelled`/`completed`/`on_hold` já ficarem de fora).
- Compromisso sem `address_id` (endereço em texto livre) é tratado como
  "sem coordenada boa", mesmo critério de OS com endereço não geocodificado.
- Nenhuma mudança na regra "ordem manual prevalece" (Task 22.5): ela
  continua valendo para o roteiro como um todo, agora com paradas mistas.

- [ ] `recalcularDistancias()` e `chegadaEstimada()` funcionam com parada
